1. Purpose & System Overview

Goal: an agentic system that automates the end-to-end Java 17 (Mule 4.9 LTS) upgrade of MuleSoft applications — assess → apply matrix-driven edits → atomic commit on a branch → open PR → verify deployment (via CI callback) → notify (Slack/Jira) → rollback on failure.

Core app: platform-lifecycle-orchestrator (Mule 4.9, Java 17).

Two front doors, one engine: every capability is exposed over REST (APIkit) and MCP (tool-listeners for agents). Both delegate to the same shared pf-* sub-flows, so behavior is identical regardless of caller.

State: Object Store v2 (OSv2) partitions — jobStore (job records, 30d), locksStore (single-flight locks, 1d), idempotencyStore (webhook de-dup, 2d), indexStore (branch→jobId index, 30d).

2. Project Structure & Reorganization

Accepted reorganized flows into a logical folder layout and renamed folders:

  • process → orchestration (entry/implementation flows: post-jobs, post-jobs-assess, get-job-status, post-webhook).
  • system → implementation (shared helpers: github, notify, reference-data, anypoint, reconcile).
  • Plus global (global-config, global-error-handler, main routing) and the MCP file.

Rationale: separate transport/orchestration from reusable implementation; REST and MCP share the implementation layer.

Convention: mf-impl-* = top-level flows; pf-* = shared sub-flows (documented with Requires:/Returns: header comments).

Request field rules Accepted

  • Required: appName, environment.
  • Optional: jiraTicketId (Jira integration skipped/auto-created when absent), approvedChangePlan (audit-only; the worker re-assesses internally and drives edits from its own freshly-computed fileEdits — the supplied plan is not trusted).

environment field — why it exists

Selects the target deployment environment for the app being upgraded; used for the Anypoint deployment-status verification (ARM/AMC lookup) and recorded on the job. Not the same as the orchestrator's own runtime env.

4. Design Decisions — Accepted (with rationale)

  1. Transport-agnostic engine. pf-* sub-flows contain all logic; REST sets HTTP concerns (202, status codes) and MCP returns JSON strings. No duplication.
  2. MCP tool responses return a JSON string via #[write(payload, 'application/json')] (not #[output application/json --- payload]). The latter drove DataWeave's Java writer over the result map and threw No read or write handler for appName. REST unaffected (the HTTP listener serializes directly).
  3. approvedChangePlan is audit-only, never trusted. The worker always re-runs assess.
  4. Optional Jira. Absent jiraTicketId → job still runs end-to-end; Jira steps skip or auto-create (see §10).
  5. Single-flight lock per app (lock::{appName} in locksStore) to reject concurrent upgrades of the same app (CONFLICT:UPGRADE_IN_PROGRESS).
  6. Self-healing reconcile (pf-reconcile, scheduled) recovers orphaned jobs.
  7. Native HTTP Basic auth for Jira/Exchange (<http:basic-authentication>), replacing manual toBase64 Authorization headers (toBase64 was unresolved).
  8. UTC-truthful timestamps everywhere: (now() >> |+00:00|) as String {format: "…'Z'"}.
  9. mergeWith for object merges (not ++) — see §8.
  10. output application/java --- prefix on logger/raise-error/set-variable expressions to avoid media-type inference errors — see §8.
  11. Config split by constancy: config.yaml = env-constant; config-<env>.yaml = varying (loaded first, wins) — see §9.
  12. Jira ticket links in PR body (Markdown link) and Slack (all success/failure/DEPLOYED messages), all guarded on jiraTicketId presence.
  13. Rollback notifications surface the revert PR URL in Slack + Jira comment on FAILED_DEPLOY.
  14. Auto-create Jira ticket (Feature 2) when none supplied and enabled — see §10.
  15. RAML published to Exchange; APIkit consumes the Exchange asset via resource:: — see §14.
  16. Blast-radius warning at assess time when edits land on a shared parent/BOM pom — see §12.
  17. RAML FileEdit aligned to the engine's real shape (file/kind/from/to + optional coordinates), so assess output round-trips into approvedChangePlan — see §14 / Backlog #2.
  18. JobStatus contract includes FAILED_INTERRUPTED in the status enum and an optional prNumber integer.

  9. Roadmap (scalability) Atomic single-flight lock (concurrency-safe). Current lock is non-atomic check-then-act (os:retrieve default false → choice → os:store); two concurrent POST /jobs for the same app can both read "no lock". Widens across CH2.0 replicas (OSv2 has no compare-and-set). Options: single replica; idempotency key (app+headSha); or a store with atomic create (DB unique constraint / queue serialization) / Java LockFactory component. MVP disposition (2026-07-07): not a correctness gap for the MVP. The race requires two concurrent submissions for the same app; the MVP runs single-replica, one app at a time, so submissions are effectively serial and the check-then-set is correct. Guardrail is operational discipline (submit → wait → next), not code. Promoted to the future roadmap as a horizontal-scale / high-concurrency hardening item (see §18).
  10. Roadmap (resilience) Durable / resumable upgrade pipeline. The multi-stage upgrade runs in <async> (in-memory, non-persistent). A restart/crash/redeploy/autoscale mid-run orphans the job; pf-reconcile later marks it FAILED_INTERRUPTED (manual resubmit) and a partial commit/branch may remain. Options: durable queue (persistent VM / Anypoint MQ / DB work item) with an idempotent, checkpointed consumer that resumes each stage. A DLQ on Anypoint MQ would capture poison/failed work items for inspection + replay. NB: full durability requires making pf-open-pr idempotent (redelivery must not open a duplicate PR). MVP disposition (2026-07-07): not a correctness gap for the MVP. On a single replica a mid-run restart still cannot auto-resume, but pf-reconcile already sweeps the orphan to FAILED_INTERRUPTED and releases the lock — no stuck state, no data loss, just manual re-submit. Acceptable for a single-replica / one-app-at-a-time MVP; promoted to the future roadmap for multi-replica / autoscale resilience (see §18).

MVP scope note (2026-07-07): #9 and #10 are explicitly scoped out of the MVP. Under the MVP operating envelope — single replica, one application upgraded at a time — neither manifests: #9's race needs concurrency, and #10's orphan is already recovered by pf-reconcile. Both are retained as future-roadmap scalability/resilience items that justify how the solution scales to multi-replica, high-concurrency operation. #1 (HMAC cd-result) and #3 (branch protection) are approved to implement but on hold pending the "Vibes" flow-decomposition pass (see §17) — revisit after.

8. Key Engineering Learnings & Conventions

DataWeave strictness

  • output application/java --- on inline expressions (loggers, raise-error, some set-variable) to prevent "more than one media type" inference errors.
  • mergeWith (not ++) for object merges. object ++ object appends duplicate keys rather than overwriting, which silently corrupted job records (old status persisted).
  • Type inference on coords: (vars.coords - 'defaultBranch') ++ { defaultBranch: … } to avoid duplicate keys + serialization handler errors.

Timestamps

Always (now() >> |+00:00|) as String {format: "yyyy-MM-dd'T'HH:mm:ss'Z'"} — the >> |+00:00| shifts to UTC so the Z label is truthful (previously local IST mislabeled as UTC).

Object Store

  • os:retrieve with a null default treats it as "no default" and throws OS:KEY_NOT_FOUND; use a real default (#[false], #[{}]).
  • Lock release must be idempotent (os:contains guard) and non-fatal to avoid verbose runtime exceptions on reconcile sweeps.

WARN vs ERROR (logging levels)

The distinction is "did the primary business outcome fail?", not "did something go wrong?".

  • ERROR = the operation failed and someone must act — used at fatal boundaries: the global error handler, the async-pipeline fatal handler (marks FAILED_*), coordinate-resolution failure. Page-worthy: the requested upgrade did not happen.
  • WARN = handled/degraded/self-healed; the primary outcome still succeeds — used in on-error-continue swallow handlers (Slack/Jira down, auto-create Jira failed), and in pf-reconcile recovering an orphan (an operational signal, not a live crash).
  • Heuristic: inside on-error-continue that swallows → WARN; inside global/propagating handler or a path that sets FAILED_* → ERROR; expected/optional-missing (no jiraTicketId) → DEBUG/INFO (keep WARN meaningful enough to alert on).

Flow vs sub-flow

 <flow><sub-flow>
Event source (listener/scheduler/MCP/APIkit target)✅❌
Own <error-handler>✅❌
Own processing strategy / boundary✅❌ — runs synchronously in caller's thread, shares its context/vars
Callable via flow-ref✅✅
  • Must be a flow if it needs a trigger, its own error handler, or an async/processing boundary. Otherwise prefer sub-flow (lighter, inherits context).
  • The APIkit routing flows (post:\jobs\assess:…) must be flows — APIkit routes to them by name. pf-get-job-status is a sub-flow (pure, shared by REST + MCP); mf-impl-get-job-status is a flow (its REST-facing boundary).

Mule pricing — the "MuleSoft Flows" meter (corrected)

Refs: Mule Credits, Usage Metrics.

  • Under the usage-based Mule Credits model, MuleSoft Flows is a billable meter (it is not a cost factor under classic vCore-based subscriptions).
  • Counts: a <flow> with a Mule event source (http/jms/ftp/db/scheduler listener, MCP tool-listener, …) OR an APIkit routing flow that processes requests.
  • Does NOT count: <sub-flow>; plain <flow> with no source that only modularizes code (called via flow-ref).
  • Aggregated Max Concurrent (peak-hour flow count in the month) × workers/replicas; charged only while deployed and running.
  • This app's billable flows (× replicas): 10 — 1 HTTP listener (…-main) + 5 APIkit routes + 3 MCP tool-listeners + 1 scheduler (pf-reconcile). All mf-impl-* and pf-* are free.
  • Levers: replica count (multiplier); drop optional surface area (e.g. the 3 MCP flows if unused); decompose freely into sub-flows (free). Don't merge distinct API endpoints just to save flows.

10. Jira Integration

Feature 1 — lifecycle comments (pf-jira-comment)

  • Posts an ADF comment (summary paragraph + optional link node) to the ticket at lifecycle transitions (PR opened, deployed, failed/rollback).
  • Self-guarding (when jiraTicketId != null) + non-fatal (on-error-continue, WARN).
  • pf-notify was refactored to reuse pf-jira-comment (removed duplication).

Feature 2 — auto-create ticket (pf-jira-create-issue) Implemented

  • New non-fatal sub-flow in notify.xml, called as the first step of the <async> pipeline in pf-start-upgrade (pre-assess).
  • Fires only when no jiraTicketId supplied AND jira.autoCreate=true. POST /rest/api/3/issue (ADF body) to jira.projectKey as jira.issueType; adopts the returned key as vars.jiraTicketId; merges it into the job record so all downstream steps (assessment comment, PR body, Slack, final decision, GET /jobs/{id}) reference the real ticket.
  • Non-fatal: creation failure → upgrade proceeds ticket-less (WARN); never blocks.
  • Off-by-default in prod (config default false), on in dev.

Notification links

  • PR body: Jira as Markdown link [TICKET](baseUrl/browse/TICKET).
  • Slack success/failure/DEPLOYED: Slack-linked Jira: <url|TICKET>.
  • All guarded on jiraTicketId presence.

11. Notifications (Slack) & Rollback

  • pf-notify (success/PR-open), pf-notify-failure (failure — reads authoritative status/error from the job record), DEPLOYED message on cd-result success.
  • All non-fatal (try + on-error-continue, WARN) — a notification outage never fails the pipeline.
  • Rollback visibility: on FAILED_DEPLOY, pf-rollback always opens a revert PR; the Slack failure message and Jira comment include the revert PR URL (vars.revertPrUrl, falling back to the original PR). Decision: never auto-close the forward PR (§5).

12. Concurrency, Durability & Self-Healing

  • Single-flight lock lock::{appName} — see Backlog #9 (non-atomic; hardening deferred).
  • pf-reconcile (scheduled sweep): recovers stale jobs in early non-terminal states (PROCESSING, ASSESSING, COMMITTING, COMMITTED) → marks FAILED_INTERRUPTED, releases the lock via idempotent pf-release-lock. Dev cadence 30s / 120s stale; prod 5min / 15min.
  • Durability gap (Backlog #10): <async> is in-memory; a mid-run restart orphans the job (reconcile only later flags it; partial branch/commit may remain). Not observable in single-user local testing; matters for production and multi-replica.
  • Blast-radius (assess): when property/dependency/plugin edits resolve to a shared parent/BOM pom (any chain entry other than the app's own module pom at chain[0]), pf-assess-app appends a BLAST RADIUS: … warning listing the shared file(s). Rationale: editing a shared BOM upgrades every inheriting module (real example: mule-apps bom/pom.xml bump broke apps-commons CI). Propagation to Slack/Jira deprioritized (§5).

13. Security — Webhook Authentication

  • POST /webhook (GitHub): HMAC-SHA256 over the raw body vs x-hub-signature-256 (github.webhookSecret). Raw body + headers captured in main before APIkit parses.
  • POST /webhook/cd-result (CI): shared X-CD-Token header == github.webhookSecret (plaintext). Backlog #1: upgrade to HMAC-SHA256 over the raw body.
  • Machine-to-machine only — no token in request body (rejected, §5).

16. Logging Framework — Finalized Design Design-only, not implemented

Reference studied: apps-commons/logger-common.xml — 6 milestone sub-flows (csf-logger-*) each rendering a structured-JSON envelope from an external DWL template (dwl/log/v-log-*.dwl), all at INFO. Fields: externalTrackingId, globalTransactionId, muleTransactionId, applicationName, processName, flowName, environment, source, target, httpMethod, milestoneStatus, customerId.

Why a variant, not a copy: the orchestrator is async/job-based (events happen after the HTTP response), multi-protocol (REST + MCP + webhook + scheduler), and needs WARN/ERROR (their framework is INFO-only).

The model (three parts)

  1. Ambient context in MDC, set once. Stable-per-request fields (correlationId [Mule sets it], jobId, appName, env) pushed to MDC via the Tracing module (tracing:set-logging-variable) at the ~6 entry points and at jobId mint/load. Emitted on every line by log4j2 — loggers never re-type them. Safe from nesting because these fields don't change per sub-flow.
  2. START/END bracket each flow/sub-flow. Exactly two <logger>s; the flow name is a literal in the message (NOT a pf-log-start sub-flow — #[flow.name] in a sub-flow returns the owning top-level flow, and a shared vars name breaks under nesting).
  3. Selective INFO/WARN/ERROR only where they add signal; delete redundant "milestone" INFO (a child sub-flow's own START/END already proves the step ran).

log4j2 change: extend the pattern to emit MDC — %-5p %d [%t] corr=%X{correlationId} job=%X{jobId} app=%X{appName} env=%X{env} - %m%n (or JsonLayout properties="true" for Splunk). Also update log4j2-test.xml.

Level rules: INFO = START/END + real decisions (PR opened, DEPLOYED/FAILED verdict); WARN = swallow handlers + business guards (lock held, duplicate delivery, verify-disabled, Jira/Slack failed); ERROR = global + async-fatal handlers + FAILED_*; DEBUG = payload snapshots.

Decisions

Decided Coverage: top_and_meaty — START/END only on top-level flows + meaty sub-flows, skip tiny helpers. Net ~40 loggers (down from 95).

  • Gets START/END: mf-impl-post-jobs, mf-impl-post-jobs-assess, mf-impl-get-job-status, mf-impl-post-webhook, mf-impl-post-cd-result, 3 MCP tool flows, pf-reconcile; meaty sub-flows pf-start-upgrade, pf-assess-app, pf-apply-transforms, pf-atomic-commit, pf-open-pr, pf-rollback, pf-resolve-coordinates, pf-load-matrix, pf-verify-deployment, pf-notify, pf-notify-failure, pf-jira-create-issue.
  • Skipped: pf-release-lock, pf-set-status, pf-get-job-status, pf-jira-comment, pf-get-anypoint-token (keep only WARN/ERROR where relevant).
  • main already brackets via request/response; the 5 APIkit routing flows are skipped.

Decided log4j2/MDC hardening: the earlier standalone JsonLayout question was answered No (envelope-as-message is enough); the finalized model above nonetheless centers on MDC because correlationId is already wired in log4j2.xml.
